# 03 · 架构优化设计

本文的每条结论都来自 2026-10-18 在服务器 124.220.54.64 上跑的探针，不是纸面推演。
编号按执行顺序：P1=ACL 方案（实测否掉，见 §6 末，当时没单独编号）、
P2=Directus 首启、P3=uid 形态与并发、P4=超管可见列、P5=集合可见性、
P6=策略载荷形状、P7=系统表 DDL、P8=SQL 播种、P9=字段白名单验证。
**凡是没实测过的，都明写"未验证"**。

## 1. 一句话架构

**后台是旁路，不是主链路。** Directus 只负责"看记录和改记录"，
所有高危动作（注销、封号、抬门、备份）走我自己写的运维 API；
两者都不在主应用的请求路径上——后台全挂，App 不受影响。

```
   运营者浏览器
        │  https://124.220.54.64/admin/          ┌─ Basic(应用内，常数时间比对) + 令牌/cookie
        │  https://124.220.54.64/ops/            └─ limit_req（登录口 6 次/分，页面 30 次/秒）
        ▼
  ┌───────────────┐   proxy   ┌──────────────────────────────┐
  │  qingsu-tls   │──────────▶│ Directus 容器 (172.17.0.1:8055) │
  │  nginx :443   │  /admin/  │ Studio 在 /admin，API 在源站根路径 │
  │               │──────────▶├──────────────────────────────┤
  │  /ops/ 前缀   │  proxy    │ 运维 API 172.17.0.1:8100 (systemd) │
  └───────┬───────┘           │ 注销/封号/抬门/备份/聚合计数      │
          │                   └───────────┬──────────────────┘
          ▼                               │ 同一个文件的第二条写连接
  ┌───────────────┐                        ▼
  │ qingsu.service│            ┌───────────────────────┐
  │ uvicorn :8000 │─────写────▶│ /opt/qingsu/data/      │
  │ 主应用（单进程）│            │   qingsu.db  WAL busy=5s│
  └───────────────┘            └───────────────────────┘
        ▲
        │ 密钥在 /opt/qingsu/keys（容器不挂它，读不到）
  /opt/qingsu/keys/media-signing.key  0600 qingsu:qingsu
  /opt/qingsu/keys/ws-secret.key      0600 qingsu:qingsu
```

> 绑 `172.17.0.1` 而不是 `127.0.0.1` 是实测结论 K-19：nginx 在另一个容器里，够不到本机回环。
> `172.17.0.1` 是 docker 桥地址，公网不可路由。

## 2. 选型：为什么是 Directus

| 候选 | 判定 | 理由 |
| --- | --- | --- |
| **Directus 11** | ✅ 采用 | 它是"把已有库包装成管理界面"，不是"另建一个库"。业务表结构由主应用决定，平台跟着读——这正是后台唯一需要的能力 |
| NocoDB / Baserow | ❌ | 同样是包装已有库，但它们**自己维护一层元数据表**，对 SQLite 的外部库改动更脆弱；且没有 Directus 这种字段级权限模型 |
| Appsmith / ToolJet | ❌ | 它们做的是"自己拼界面"，每一页都要手写 SQL 与控件；等于我用低代码平台再写一遍前端，成本高于直接写 |
| phpMyAdmin / Adminer | ❌ | "任意 SQL"是它们的主要交互方式，与本项目的第 3 条范围约束（不允许无约束写生产库）正面冲突 |
| 手写 FastAPI + Vue 管理端 | ❌ | 覆盖面（34 张表 × 增删改查 × 筛选分页 × 权限）保守估计 3000 行，且要自己长期维护；机主只需要运营一个人用 |
| 直接用 SQLite 命令行 | ❌ | 这正是现状——机主每次都要 SSH，三个 P0 缺口就是这么攒出来的 |

**选它的代价**（写清楚，别只说好处）：它会把 40 张 `directus_*` 系统表写进业务库文件（P5 实测），
从此这个文件有两个写入者；它自带的超级管理员绕过一切字段权限（P4/P9 实测）。
§4、§5 就是为了对付这两条。

## 3. 实测到的平台硬约束（每条都影响设计）

| # | 实测结论 | 来源 | 影响 |
| --- | --- | --- | --- |

## 4. 由实测定下的三个设计决策

**D-1 双平面，不按功能分屏而按"能不能出事"分**
数据控制台（Directus）只做低风险字段编辑：改反馈状态、写回复、下架帖子、处理举报。
运维 API（自研）做不可逆/影响面大的动作：注销、封号、重置密码、撤销会话、抬门、备份。
分界的判据是一句话：**这个操作做错，能不能靠"改回去"救回来？** 能 → 控制台；不能 → 运维 API。

**D-2 白名单，不黑名单**（K-8/K-13 的直接结果）
每个集合的权限行都显式列出"允许哪些列"，而不是"禁掉哪些列"。
差别在新增列时的默认行为：黑名单下新加的敏感列默认可见，白名单下默认不可见。
`users.banned_at` 这次能显示出来，正是因为我把它加进了白名单——反过来说，
以后任何人往业务表加一列，后台看不见，必须显式加白名单，这才是想要的默认。

**D-3 计数只有一个来源**
M-51 的每个数字由运维 API 从明细表 `COUNT(*)` 现算（K-12 也让控制台算不了这些）。
控制台顶栏要显示"帖子数/私信数"时，调运维 API 的 `/overview`，不许在前端自己拼 COUNT。
理由和分层统计加和那条规矩一致：宁可只有一个地方算错，也不要两处数字对不上。

## 5. 与主应用的耦合点（每个都要能单独回退）

| ID | 改主应用什么 | 为什么必须改 | 回退方式 | 风险面 |
| --- | --- | --- | --- | --- |
| C-1 | `users` 加 `banned_at`/`ban_reason` 两列，`get_current_user`（`server.py:837`）的**现有那条 JOIN 查询**里一并取出并判封号 | 主应用现在**完全没有封号概念**（`grep -c "banned\|is_active\|disabled" server.py` = 0），后台标了也没有任何强制力 | 列留着不判即可（回退只删 3 行判断）；不动数据、不重建表 | 判在登录热路径上，所以必须复用同一次查询，不能加第二次 `execute`；写错会全站 403 |
| C-2 | 数据目录权限：`/opt/qingsu/data` → `2770 qingsu:qingsu`，`qingsu.db` → `660` | K-2/K-3：第二个写入者要能建 `-wal` | `chmod 755` / `chmod 644` 复原，容器随即失去写权限（变成只读后台） | 主应用是 owner，改 group 位不影响它；实测 health 200 通过 |
| C-3 | nginx `qingsu-tls` 加 `/admin/`、`/ops/` 两个 location | 不给公网直开 8055/8100 | 删掉这两段 + `nginx -s reload`，其余路由不受影响 | 见 §9 的 inode 陷阱；写坏会连带 `/ws/` 一起挂 |
| C-4 | 两个 0600 密钥挪出 `DB_DIR`：加 `KEY_DIR = os.environ.get("QINGSU_KEY_DIR", DB_DIR)`（`server.py:3266`、`server.py:3450`） | K-4：容器只挂数据目录，密钥不在里面就读不到 | 不设该环境变量 = 行为与现在完全一致 | 密钥文件是 `O_CREAT\|O_EXCL` 自动生成的，挪走要给旧文件搬位置；**挪错等于所有已签名的图片 URL 立刻失效** |

C-4 附带一个必须一起做的诚实性改动：`media_key()`/`ws_secret()` 现在**发现文件不存在就静默新建**，
意味着密钥一旦被误删，签名 URL 全失效但没人知道。补一行日志 + `/health/ready` 里报
`keys_regenerated=true`，让"我把它弄丢了"变成能看见的事（这是运维端点做对的唯一方式）。

## 6. 部署形态（照抄可用，不要"优化"）

### 6.1 容器

```
image:  directus/directus:11            # 11.17.4，1.16GB，已在服务器本地
user:   "1000:1000"                     # K-1：用应用 uid 会起不来
group_add: ["993"]                      # qingsu 组，写库靠它
volumes: /opt/qingsu/data:/data         # 只挂数据目录；密钥不在里面（C-4）
ports:   172.17.0.1:8055:8055          # docker 桥地址（nginx 够得到、公网不可路由）；绝不对 0.0.0.0
env:     DB_CLIENT=sqlite3
         DB_FILENAME=/data/qingsu.db
         DB_SQLITE_BUSY_TIMEOUT=5000     # 必须和主应用的 5000 同级，否则撞锁直接报错给运营
         KEY=<root:600 文件>  SECRET=<root:600 文件>
         ADMIN_EMAIL=<真实 TLD，如 ops@qingsu.app>   # K-6
         ADMIN_PASSWORD=<root:600 文件里生成的强随机值>
         TELEMETRY=false  LOG_LEVEL=info
```

`KEY`/`SECRET` 是两个随机串，**只落在服务器的 root:600 文件里**，不进仓库、不进日志、不进任何接口响应。
超管口令同理；日常运营用 §6.3 建出来的策略账号，超管只在"把策略改坏了"时拿出来用。

**为什么不用"独立 uid + POSIX ACL"这条路**（我先试过，实测记为 P1）：
给 `qingsu-admin` 建独立 uid 并把数据目录只加默认 ACL（`default:group:qingsu:rw`）之后，
第一笔写就失败——`sqlite3.OperationalError: attempt to write a readonly database`，
因为目录本身对第二个 uid 不可写，它连 `-wal` 都建不出来。要补的是目录组写位，
再往下还有"跨 uid 谁来删 `-wal`"（加 sticky bit 会让最后一个关闭连接的人删不掉别人的 WAL 文件）。
**那条路径我没有实测通过，所以不赌**；现在的形态（镜像原生 uid + 附加组 + setgid 目录）
每一步都有 P2/P3/P7/P9 的实测输出背书。

### 6.2 运维 API

systemd 直跑（不容器化）：它要执行 `backup.py`、读写 `min_build`、发临时请求打本机 API，
容器化只会把这些变成挂载和跨网络调用。监听 `172.17.0.1:8100`（K-19），`User=root`（备份与门文件需要），
并设 `UMask=0002`——root 建的 `-wal/-shm` 必须是组可写，否则主应用（uid qingsu）下一次写就会
`attempt to write a readonly database`。身份分两层：外层 HTTP Basic（应用内常数时间比对，
口令缺了直接 503，不静默敞开）+ 应用层运维令牌（`X-Qingsu-Token` 头，或登录后的会话 cookie）。
每个动作写一行 `admin_audit`。

### 6.3 策略与权限只能 SQL 播种（K-10/K-11）

```sql
INSERT INTO directus_policies (id,name,icon,description,enforce_tfa,admin_access,app_access)
VALUES (:pid,'轻塑运营策略','lock','后台日常运营',0,0,1);
INSERT INTO directus_access (id, role, policy) VALUES (:aid, :rid, :pid);
INSERT INTO directus_permissions (collection, action, policy, permissions, fields)
VALUES ('users','read', :pid, '{"_and":[]}',
        '["id","username","nickname","public_id","created_at","banned_at","ban_reason"]');
```

播种完 **必须 `docker restart`** 一次（Directus 缓存权限；P9 里没重启前新角色读不到东西）。
每条权限行的 `fields` 都要显式给全（K-9），所以播种脚本从 `PRAGMA table_info` 取列名，
减掉敏感列清单，生成白名单——**不手写列清单**，手写迟早和真实表结构脱节。

## 7. 安全四层：每层挡什么、挡不住什么

| 层 | 机制 | 挡住 | 挡不住（要明说） |
| --- | --- | --- | --- |
| L1 网络 | 8055/8100 只绑 `172.17.0.1`（docker 桥地址，公网不可路由） | 公网直连、扫描 | 服务器上的任意本地进程/容器 |
| L2 入口 | nginx 只走 443 + `limit_req`（登录口 6 次/分 burst 5，页面 30 次/秒）；**Basic 在运维 API 里做**（nginx 容器只挂了单个 conf 文件，htpasswd 无处安放且容器一重建就会让 nginx 起不来） | 无凭证的爆破、脚本撞库 | 拿到口令的人；Directus `/admin/` 这一侧没有 Basic，只靠它自己的登录 + 登录口限流 |
| L3 平台 | 策略账号 + 字段白名单（K-8 实测：显式要凭据列 → 403，`*` 只出白名单） | 运营账号看到凭据列 | 超级管理员（K-7 实测绕过一切）——所以超管口令不进仓库、不进日常使用 |
| L4 代码 | 运维 API 自己拼响应字段 + 高危动作显式确认 | 屏蔽清单被绕过、误删 | 我自己写错白名单——所以测试文档 T-70 要拿"真接口响应"逐列比对，不看界面 |

**已知敞口（不藏着）**：服务器只有 IP 没有域名，L2 的 Basic 走的是裸 IP 证书；
口令在传输层依赖 TLS，但 `Strict-Transport-Security` 对 IP 访问的浏览器约束有限。
`/admin/` 这一侧连 Basic 都没有（Directus 的 `Authorization: Bearer` 与 Basic 抢同一个头，
叠上去会互相顶掉），所以它的补偿是：运营账号随机口令 + 登录口 6 次/分 + 只出 443。
另外 uid 1000 在本机映射到 `lighthouse` 账户，容器新建的文件在 `ls` 里显示成 `lighthouse:qingsu`，
看目录的人可能误以为权限坏了——这是 K-3 的副作用，已记入故障模式表 F-5。

## 10. 部署顺序（顺序错了会当场踩雷）

```
1 备份 + integrity_check      ← 没通过就不许往下走
2 主应用 C-1 封号字段与判定    ← 先让"封号"真的有效，再建界面
3 主应用 C-4 密钥目录 + 回归   ← 挪完必须重签一次图片 URL 验证
4 数据目录权限 C-2            ← 立刻验健康，失败就 chmod 回去
5 Directus 容器 bootstrap     ← 邮箱先预检（K-6）；compose 先 `config -q` 验结构
6 SQL 播种策略/权限 + 重启容器  ← 白名单由 table_info 生成、**逗号分隔**（K-9/K-10）
7 运维 API 起服务             ← 先只监听桥地址，全部动作跑一遍假数据
8 nginx /admin/ /ops/ + API 根路径 <!-- 最后一步才暴露 -->
9 联动自证 + 全量测试 + App 侧回归
```

第 8 步放最后，是"字段权限还没配对就把生产数据暴露到公网"这个顺序错误的唯一防线。

**这一轮真的踩过的三个坑（顺序与校验都补进脚本了）**：

1. **拿"最旧的备份"还原**：`ls -t | tail -1` 取到的是最老的一份，里面还没有 `/ws/` 段——
   私信实时通道当场断了。现在还原前先 `grep "location /ws/"`，装之前也先验现役配置"该有的都在"。
2. **改了 YAML 却没验内容**：脚本把 `ports:` 那一行改没了，`md5sum` 双向都对（传的是坏文件）。
   现在 `bootstrap.sh` 先跑 `docker compose config -q`，不合法不启动。
3. **注释把幂等标记一起剥掉**：插入脚本过滤注释行时把标记也删了，第二次安装又插一遍 `limit_req_zone`
   → `nginx -t` 报"already bound"。现在幂等判据看 `zone=adminpage`，且保留注释。

**nginx 的 inode 陷阱**（现役 `scripts/deploy.py:78` 就是这么做的，别改写法）：
`/opt/qingsu/tls/default.conf` 是 bind 进 `qingsu-tls` 的同一个 inode。
用 `cat > /opt/qingsu/tls/default.conf`（原地截断写）容器立刻看到新内容；
用 `install`、`cp`、`mv` 或编辑器"另存"会换掉 inode，容器仍持有旧文件——
`nginx -t` 和 `nginx -s reload` 都会"成功"，但线上跑的还是老配置。
改完必须 `docker restart qingsu-tls`，并且**拿线上响应核对**，不能只看 reload 返回 0。
（本轮 `install-nginx.sh` 每次都比对操作前后的 inode，并独立回读 `/ws/`、两份清单、主应用路由。）

## 11. 本轮刻意不动的主应用优化（各写清代价）

| # | 想做的事 | 为什么这轮不做 | 现在的代价 |
| --- | --- | --- | --- |
| N-1 | `server.py`（~4400 行）继续拆进 `app_modules` | 与后台无关；拆错了是主应用故障，混在一起做会让"后台上线"这件事失去干净的回归边界 | 单文件仍难读；判据只保证行为不保证结构 |
| N-2 | 多 worker（`uvicorn --workers 2`） | 实测 `qingsu.service` 无 `--workers`，`_WS_HUB` 是**进程内**字典 → 加 worker 会随机私信掉线。要先做 Redis pubsub 广播，那是另一件事 | 单进程 CPU 上限；当前用户量远未触及 |
| N-3 | SQLite → PostgreSQL | Directus 接 PG 更顺（视图、并发都好看），但迁移要把 34 张表 + 幂等回执 + 撤回语义整体搬，且后台上线不该同时改主存储 | 两个写入者共享一个文件（已实测成立，K-5） |
| N-4 | 媒体上对象存储/CDN | 后台的 M-35 只需要文件清单与孤儿检测，不需要新存储层 | 图片仍走本机 HMAC 签名 URL，15 分钟有效 |
| N-5 | 把凭据列搬出业务库（彻底解决 K-7） | 要改登录/注册/会话三条链并迁数据，属于主应用级重构；这轮用"超管隔离 + L2/L3"兜住 | 超管口令泄露仍能拖走哈希——离线爆破仍可能，这是残余风险 |
