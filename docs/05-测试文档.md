# 05 · 测试文档

这份文档是后台的**验收合同**。每条用例都写清三件事：怎么做、什么算过、
以及**它在故意做错时必须红**（反样本）。只写"应该能打开"的那种用例不算判据。

## 0. 三条判据原则（先于任何用例）

1. **自证那一下真发生了。** 断言"改状态成功"不许只看 HTTP 200——必须**从另一条路径读回**
   （宿主侧 SQL 直读，或主应用 App 接口读），两边一致才算。
   本轮探针就是这么抓出 Directus 的 403 的：界面看着"点了没反应"，读回才知道根本没写进去。
2. **判据要拿正反样本标定过才算存在。** 每条安全类用例都要先证明"在正确实现下它是绿的，
   在故意破坏的实现下它是红的"。标不出红的判据，视同不存在，写进 §5 变异清单。
3. **失败要红，不能静默跳过。** 环境不满足时（比如没开 `HOUKAI_LIVE`）要显式打
   `SKIP 原因=xxx` 并计入总数；任何"因为缺依赖而 pass"都算缺陷。
   例外只有一条：**打生产的用例默认跳过，且必须打印"本轮未验证生产"**。

## 4. 专项用例

### T-70 敏感列扫描（**整个后台最重要的一条**）

做法：对**每一个**会出数据的出口，各请求一次"最大字段集"，把响应里出现的列名收集起来，
与 `02 §3` 的黑名单求交集。交集非空即红，且**必须打印出是哪一列、从哪个出口出来的**。

出口清单（一个都不能漏）：
```
GET /admin/ 集合列表页 / 详情页 / 列表导出 CSV
GET /ops/api/overview  /api/users/{id}/export  /api/health
后台运维页 HTML 源码（前端不许内嵌任何数据）
Directus items 接口：策略账号 fields=* 与 显式要敏感列（期望 403）两种都要试
Directus 的 CSV 导出：每个集合 ?export=csv 都要扫（本轮未测）
```

正样本（上线实测）：策略账号显式 `fields=password_hash` → **403**
`You don't have permission to access field "password_hash"`；`fields=*` 只出白名单列；
`fields=id,username,nickname` 正常返回。
反样本（P4/P9 实测）：超管 `fields=*` → 9 列全出，含 5 个凭据列。
→ 所以本条的判定是**分账号的**：
- 策略账号必须 0 命中（硬红线）；
- 超管命中是**已知且接受**的残余风险（03 §7 L3 表格里写死了），
  但必须同时断言：超管口令不在仓库、不在任何响应、不在日志里出现（静态扫描）。

变异标定：把白名单生成器里 `password_hash` 减掉那一行注释掉 → 本条必须红。
（如果它不红，说明扫描根本没在跑真接口，判据是假的。）

### T-80 主应用热路径不回退

C-1 给登录判定加了列，必须证明**没有多出一次 DB 往返**：

1. 静态判据：`get_current_user` 函数体内 `conn.execute(` 出现次数 == 改动前的次数（现为 1）。
2. 行为判据：在同一副本库上跑 200 次 `/api/dashboard`（带 token），与改动前的基线比，
   p95 延迟劣化不得超过 10%；两次都要打印实测毫秒。
3. 反样本：把判定写成"另外查一次 users 表" → 第 1 条必须红。

基线数字不许手写，跑之前先测一遍存成 `tests/baseline.json`。

### T-90 双写入者并发（02 §5 的兑现）

在服务器副本库上：
- 线程 A：以 Directus（容器）改一条反馈的 `status`，200 次；
- 线程 B：以 `qingsu` 身份写一条 `food_logs`，200 次；
- 判定：两侧成功数都必须 == 200，`busy`/`locked` 必须 == 0，结束后 `integrity_check`=ok，
  且两边的行都还在（各自 COUNT 对得上）。

P3/P7 实测参考值：宿主侧 `ok=200 busy=0 other=0`，停容器后 `integrity_check=ok`、200 行全在。
反样本：把容器侧 `DB_SQLITE_BUSY_TIMEOUT` 设成 0 → 必须出现 busy/报错并把这条判成红
（证明 `busy_timeout` 那行不是装饰）。

### T-91 权限与密钥隔离（K-2/K-3/K-4 的持续生效）

| 断言 | 期望 |
| --- | --- |
| 数据目录 / 库文件权限 | `2770` / `660`，`stat` 直读 |
| 容器 `-wal/-shm` 归属 | group 必须是 `qingsu`（P3 实测 `lighthouse:qingsu 660`） |
| 容器读密钥 | `Permission denied`（把 keys 目录故意挂进去再验一次，防"以后有人图省事挂载整个 /opt/qingsu"） |
| 主应用 health | 200，`systemctl is-active qingsu`=active |

### T-92 容器运行形态不许被人"顺手优化"

断言 compose 文件里写死：`user: "1000:1000"`、`group_add: ["993"]`、
ports 必须是 `127.0.0.1:8055:8055`（不能是 `8055:8055`）。
反样本：改成 `993:993` → K-1 会起不来；改成公网监听 → 本条必须红
（这台机器没有防火墙，只有安全组，`0.0.0.0` 等于直接对外）。

### T-93 nginx 层

- `/admin/`、`/ops/` 无 BasicAuth 凭据 → 401；带凭据 → 200/307；
- `limit_req` 生效：登录口连打 14 次必须出现 503（实测配置 6r/m、burst=5）；页面 30r/s 不误伤静态资源；
- `nginx -T` 里 `/ws/` 那段的 `proxy_http_version 1.1` + 两颗 Upgrade 头**仍在**（C-3 的最大风险就是碰坏它）；
- 两份清单 `latest.json`、`latest-extensions.json` 仍能从 80 端口取到且 sha 与上次一致。

### T-94 备份与回退可执行性

不许只写"回退=恢复快照"。必须真做一次：
```
1) 记当前 md5 → 2) 备份 → 3) 在副本上制造一次"后台把某行改坏" →
4) 用快照恢复到临时路径 → 5) 比对恢复出来的行 == 原始 md5 的那份内容
```
生产文件全程不被写入（恢复只恢复到临时路径）。恢复流程跑不通，M-62 就只是装饰。

### T-95 后台↔App 联动（01 §4 DoD 第 3 条）

三件事必须在 **App 侧**观察到，不是后台自己看自己：

| 后台动作 | App 侧必须观察到 |
| --- | --- |
| 封号（M-15） | 该账号请求 `/api/dashboard` → 403 且文案一致 |
| 回复反馈（M-23） | `/api/feedback/mine` 里该条出现回复与状态 |
| 下架帖子（M-32） | `/api/community/feed` 与作者主页都不再出现该帖 |

夹具账号命名 `houkoucheck_<随机>`，跑完按 id 显式删除全部子表行，
删前打印"将删 N 张表 M 行"，删后 `foreign_key_check`=0 且真实账号行数不变（与主应用清号规矩一致）。

### T-96 环境复原自检

每轮测试结束后固定跑一遍：

无 /opt/qingsu/_dprobe 残留；无 qsp-* 容器；无 houkoucheck_* 账号；

代表标定失效**——这条在主应用上吃过一次教训（`--mutant` 报"红 0 条"要当红灯处理）。

## 6. 明确不覆盖什么（写清楚，别让读者以为测过了）

1. **不做压测**。运营者就是一个人，测的是"两个写入者共存会不会互相打坏"，不是吞吐量。
2. **不验 TLS 证书链有效性**。服务器只有 IP 没有域名，`Strict-Transport-Security` 对裸 IP 的
   约束力有限（03 §7 敞口已记）。这条要等上了域名再补。
3. **不验 Directus 升级兼容性**。11.x 小版本升级可能改 `directus_*` 表结构；
   升级前必须重跑 §4 全部专项，**不接受"升完只是看看页面"**。
4. **不验多浏览器**。后台只做了 HTTP 级检查，**连桌面浏览器都没真点过**；移动端不在范围（01 §3.5）。
5. **不验真实攻击**。限流、BasicAuth 是缓解措施，不是渗透测试结论。
6. **主应用四套判据不在本仓库**（在 `main_app_gates.sh` 里调用主仓库），本后台只保证"不破"。
7. **凭据离库（03 §11 N-5）不做**，所以 T-70 对超管那一支是"已知残余风险"而不是"通过"。
