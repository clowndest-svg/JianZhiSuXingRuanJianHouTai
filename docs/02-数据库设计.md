# 02 · 数据库设计

主应用是 **单文件 SQLite**（`/opt/qingsu/data/qingsu.db`），
连接参数实测自 `server.py:71-77`：

```python
conn = sqlite3.connect(DB_PATH, check_same_thread=False)
conn.row_factory = sqlite3.Row
conn.execute("PRAGMA journal_mode=WAL")
conn.execute("PRAGMA foreign_keys=ON")
conn.execute("PRAGMA busy_timeout=5000")
```

这三条 PRAGMA 决定了后台能不能安全地接同一个文件，见 §5。

## 2. 后台新增的对象

### 2.1 `users` 加两列（封号）

```sql
ALTER TABLE users ADD COLUMN banned_at   TEXT;      -- NULL = 正常
ALTER TABLE users ADD COLUMN ban_reason  TEXT NOT NULL DEFAULT '';
```

用 `_ensure_columns` 那套补列（`server.py:263`），**不动现有数据、不重建表**。
为什么用 `banned_at TEXT` 而不是 `is_active INTEGER`：
封号要能回答"什么时候封的、封了多久"，一个布尔值答不了；
而且临时封禁（到期自动解）以后能直接复用这一列。

### 2.2 `admin_audit`（运维动作留痕）

```sql
CREATE TABLE IF NOT EXISTS admin_audit (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  actor TEXT NOT NULL,              -- 后台账号邮箱，不是用户 id
  action TEXT NOT NULL,             -- ban / unban / delete_account / raise_gate / backup / reset_pw / revoke_sessions
  target_kind TEXT NOT NULL DEFAULT '',
  target_id TEXT NOT NULL DEFAULT '',
  before_json TEXT NOT NULL DEFAULT '',   -- 改动前的值（改状态类必须有）
  after_json TEXT NOT NULL DEFAULT '',
  note TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_audit_time ON admin_audit(id DESC);
```

**为什么自己写一张，而不用 Directus 自带的 `directus_activity`**：
Directus 的 activity 只记它自己改的东西；注销账号、抬门这些走的是运维 API，
不经过 Directus，就得自己留痕。两边都留着，对账时以 `admin_audit` 为准。

### 2.3 视图（给后台的只读聚合，避免在应用层拼 N+1）

```sql
CREATE VIEW IF NOT EXISTS v_user_overview AS
SELECT u.id, u.username, u.nickname, u.public_id, u.created_at, u.banned_at,
       p.weight_jin, p.target_weight_jin, cp.region,
       (SELECT COUNT(*) FROM posts   WHERE user_id=u.id AND status='open')   AS posts,
       (SELECT COUNT(*) FROM weight_logs WHERE user_id=u.id)                 AS weighins,
       (SELECT COUNT(*) FROM food_logs   WHERE user_id=u.id)                 AS meals,
       (SELECT COUNT(*) FROM messages    WHERE to_id=u.id AND read_at IS NULL) AS dm_unread,
       (SELECT MAX(last_at) FROM conversations WHERE a_id=u.id OR b_id=u.id)  AS last_active
FROM users u
LEFT JOIN profiles p          ON p.user_id = u.id
LEFT JOIN community_profile cp ON cp.user_id = u.id;
```

> **这条设计被实测修正了**（架构文档 K-13）：SQLite 的 VIEW 不会出现在 Directus 的集合清单里，
> 所以视图**不能当安全边界**。它只用于两件事：运维 API 的取数组织，和"父=Σ子"的计数口径固化。
> 敏感列的实际屏蔽只有两条硬保证——**字段白名单权限**（P9 实测：策略账号显式要
> `password_hash` 也只回主键）和**运维 API 自己构造响应**。超级管理员绕过一切字段权限
> （P4/P9 实测），因此超管只用于建号与修复，不作日常账号（架构文档 D-2 / L3）。

## 3. 敏感列黑名单（硬约束）

任何界面、接口响应、导出文件里都不得出现：

```
users.password_hash  users.pw_salt  users.token  users.token_hash  users.share_secret
sessions.token_hash  email_codes.code_hash  email_codes.email_hash
profiles.loc_lat  profiles.loc_lng        # 精确坐标，比属地敏感得多
ai_memory.mem_value  private_ai_answers.answer  kb_entries.answer
body_cycles.photo_url  media_uploads.name  posts.images   # 原始路径，展示要换签名 URL
```

理由分两类：
- 前四组是**凭证或可推导凭证**，泄露一次等于全站沦陷；
- 后三组是**位置和媒体定位符**，泄露了用户就被定位了。主应用对外一直是
  "属地只到省 + 图片走 HMAC 签名 15 分钟"（`server.py:3266` 取密钥、`server.py:3273` 签名，
  有效期写死 900 秒），后台不能成为这套口径的漏点。

## 4. 索引补强（后台查询模式与主应用不同）

后台的典型查询是"按时间倒序翻列表 + 按状态筛"，主应用的索引是为单用户查询设计的。

```sql
CREATE INDEX IF NOT EXISTS idx_feedback_status  ON feedback(status, id DESC);
CREATE INDEX IF NOT EXISTS idx_reports_pending  ON content_reports(id DESC);
CREATE INDEX IF NOT EXISTS idx_posts_status     ON posts(status, id DESC);
CREATE INDEX IF NOT EXISTS idx_users_created    ON users(created_at, id DESC);
CREATE INDEX IF NOT EXISTS idx_media_user       ON media_uploads(user_id, id DESC);
```

只在"确实会随数据量变慢"的地方加。当前 2 个用户，加索引**测不出性能差异**，
所以这几条的价值在于"数据长起来之后不用再回来补"，
测试文档 §4 会明确标注**这是结构正确性检查，不是性能实测**。

## 5. 并发：后台能不能和主应用写同一个文件

结论：**能，但要满足三个条件**，缺一条就要改成"后台只读副本 + 写走 API"。

1. **WAL 模式**（已满足，`journal_mode=WAL`）。WAL 允许一写多读；两个写进程
   会串行而不是互相报错。
2. **两边都设 `busy_timeout`**。主应用是 5000ms（`server.py:76`）；
   Directus 侧必须显式配 `DB_SQLITE_BUSY_TIMEOUT`，否则它默认不等，
   撞上写锁就直接 `SQLITE_BUSY` 报错给用户。
3. **后台的事务要短**。绝不在后台跑"锁全表的大 UPDATE"（比如批量改状态时
   一条 SQL 改几万行），要分批。**注销账号是例外**——它必须是一个事务，
   所以走运维 API 而不是数据控制台，且实现里用
   `PRAGMA defer_foreign_keys=ON` + 不自洽整笔回滚（这套已在主应用的
   `scripts/purge-users.py` 上验证过一次生产运行）。

**验证方式**（不是纸面推理）：已在服务器上拿生产库的副本实测过一轮——容器持有 WAL 期间，
宿主以 `qingsu` 身份 `BEGIN IMMEDIATE` 连写 200 次，结果 `ok=200 busy=0`，停容器后
`integrity_check=ok` 且 200 行全在（架构文档 K-3/K-5）。
测试文档 T-90 把这件事做成可重复判据：**并发跑"后台改一条反馈 + 主应用写一条餐食"×200 次，
两边都必须成功且 `integrity_check` 为 ok**——跑在生产库的副本上，不跑生产文件。

## 6. 备份与回退

- 后台**不新增备份机制**，复用主应用的 `backup.py`（M-62 只是给它一个按钮）。
- 部署后台前的强制动作：先跑一次备份并校验，记下快照路径。
  Directus 的系统表和业务表在同一个文件里，所以**一次备份同时覆盖两边**。
- 回退 = 停掉 Directus 容器 + 恢复快照。主应用不依赖后台任何对象，
  删掉 `directus_*` 表也不影响主应用启动（这是"后台是旁路，不在主链路上"的硬要求）。
