# 01 · 功能清单

轻塑 · 减脂塑形 App 后台管理系统（下称"后台"）。  
本清单是**范围合同**：每一项都能追到主应用 `server.py` 里真实存在的表或接口，
不写"未来可能有用"的功能。

## 0. 为什么要做这个后台（不是凭空起的念头）

主应用 r149 上线了社区、私信、意见反馈，但机主的清单里有三条 P0 至今没解，
**全部是"后台缺失"造成的**：

| 缺口 | 现状证据 | 后台要补的 |
| --- | --- | --- |
| 意见反馈没有处理方 | 全仓 `UPDATE feedback` 命中 0 次；`status`/`reply`/`replied_at` 有列无人写 | M-20 反馈工单 |
| 举报进去就沉底 | `content_reports` 只有一条 INSERT（`server.py:4136`），全仓无 SELECT | M-30 举报队列 |
| 没有账号注销 | 只有帖子/评论两条 DELETE 路由；`scripts/purge-users.py` 显式拒绝删非夹具账号 | M-14 注销 |

另外三件机主每次都要在 SSH 里手敲的事，也一并搬进界面：**抬强更门**、
**触发备份**、**看服务健康**（M-60/M-61/M-62）。

## 1. 权限模型

只有两种角色，不做复杂 RBAC——这个 App 的真实运营者就是机主一个人。

| 角色 | 能做什么 | 怎么来的 |
| --- | --- | --- |
| `admin` 超级管理员 | 全部读写 + 高危操作 | 初始化时创建，邮箱密码登录 |
| `viewer` 只读观察员 | 只能看，不能改，看不到敏感列 | 需要给协作者时再建 |

**敏感列对日常账号（策略账号）一律不出现**（不是"显示为空"，是字段根本不查）：
`users.password_hash`、`users.pw_salt`、`users.token`、`users.token_hash`、
`users.share_secret`、`sessions.token_hash`、`email_codes.code_hash`、`kb_entries.answer`。
理由：这些是"能冒充用户"或"能撤销用户"的东西，后台被看一次就等于全站沦陷。

> **实测修正**（架构文档 K-7/K-8）：Directus 的**超级管理员绕过一切字段权限**，
> 实测 `fields=*` 会把上面 5 个凭据列原样返回。所以这条承诺的成立范围是
> "策略账号 + 运维 API"，超管账号必须隔离（口令只落服务器 root:600 文件、不作日常使用、
> 外层还有 nginx BasicAuth）。这条敞口写在测试文档 T-70 与 §6.7，不当它不存在。

## 2. 模块清单

| ID | 功能 | 数据/接口 | 验收要点 |

## 3. 明确不做（避免范围膨胀）

1. **不做用户端功能**：后台不替代 App 的任何用户界面。
2. **不做 BI 报表/图表拖拽**：需要趋势的只有 M-51/M-52，用平台自带的表格+简单图足够。
3. **不做多租户、不做自定义字段系统**：业务表结构由主应用决定，后台跟着走。
4. **不在后台放支付/会员**（主应用本来也没有）。
5. **不做移动端适配**：后台是给运营者在电脑上用的。
6. **不直连生产库做写操作的"任意 SQL"**：任何写入都必须经过集合级权限，
   高危写入必须经过运维 API（有校验、有确认、有留痕）。

## 4. 完成定义（Definition of Done）

后台算"做完"，必须同时满足：

1. 浏览器打开一个 URL，输入账号密码能进去；
2. M-10 ~ M-70 每一项在界面上都点得到，且点下去有真实数据回来；
3. M-15（封号）、M-23（回复反馈）、M-32（下架帖子）三件事在后台做完后，
   **在主应用 App 里能观察到对应变化**（不是只在后台自嗨）；
4. 敏感列在界面、在接口响应、在导出文件里都不出现（判定范围＝策略账号 + 运维 API；
   超管绕过是**已知敞口**，由 T-70 的静态扫描兜住"超管口令不落仓库/不落响应"）；
5. 全部测试文档 §3 的用例通过，且失败会红不会静默；
6. 主应用回归不破：后台上线后 `verify_live.py` 仍 8 项通过。
